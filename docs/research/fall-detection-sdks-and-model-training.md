# Fall detection on Apple, Samsung, Huawei and Garmin wearables: SDK access, model training, synthetic data and deployment

*Research report — compiled 2026-11-02. All vendor documentation was read on that date unless marked otherwise; versions and dates are stated where the source gave them. Primary sources only (vendor docs/repos, peer-reviewed papers, official dataset pages, regulators). Tags: **[UNVERIFIED]** = could not be confirmed in a primary source; **[INFERENCE]** = my reasoning from verified facts, not stated by a source. Every source is listed with its access date in §7.*

## 1. Executive summary

**Question 1 — can a developer get fall information from each vendor's SDK?**

| Vendor | Native fall detection exists? | Is the fall *event* exposed to third-party apps? | Raw motion data for your own model? | Verdict |
|---|---|---|---|---|
| **Apple** (watchOS) | Yes (Series 4+/SE/Ultra) ([Apple Support](https://support.apple.com/en-us/108896)) | **Yes**, `CMFallDetectionManager` → `CMFallDetectionEvent` (timestamp + user resolution only); needs an Apple-granted entitlement ([Apple docs](https://developer.apple.com/documentation/coremotion/cmfalldetectionmanager)) | Yes: `CMMotionManager` ≤100 Hz, `CMBatchedSensorManager` 800 Hz accel / 200 Hz device-motion (workout session required), `CMSensorRecorder` 50 Hz background recording | Best-supported: event API **and** raw data |
| **Samsung** (Galaxy Watch, Wear OS) | Yes ("Hard fall detection") ([Samsung Support](https://www.samsung.com/us/support/answer/ANS00078032/)) | **Yes, via Google Health Services**: `HealthEvent.Type.FALL_DETECTED` through `PassiveListenerService.onHealthEventReceived` ([Samsung Developers blog](https://developer.samsung.com/health/blog/en/events-monitoring), [Android reference](https://developer.android.com/reference/androidx/health/services/client/data/HealthEvent.Type)); no vendor approval documented for this path | Yes: Android `SensorManager` accel/gyro; Samsung Health Sensor SDK `ACCELEROMETER_CONTINUOUS` 25 Hz (partner approval needed to distribute) | Event API **and** raw data; approval only for Sensor SDK |
| **Huawei** (HarmonyOS watches) | Yes ([Huawei Support](https://consumer.huawei.com/en/support/content/en-us16066705/)) | **No fall event found** in Wear Engine, Health Service Kit or Sensor Service Kit docs [UNVERIFIED negative] | Yes on HarmonyOS wearables: `@ohos.sensor` ACCELEROMETER/GYROSCOPE (system-granted permissions); min sampling period 5 ms (≤200 Hz, device-dependent). Wear Engine does **not** relay raw sensors to phone apps | Raw data only; own model needed; background limits unclear |
| **Garmin** (Connect IQ / Health SDK) | Incident Detection on many devices; Fall Detection **only Venu 4** ([Garmin Support](https://support.garmin.com/en-US/?faq=RfaXahBWkH8Q7pVFLsuUmA)) | **No.** Garmin states Incident/Fall Detection "do not function with third-party Connect IQ apps"; no API found | Yes: `Sensor.registerSensorDataListener` accel/gyro (device-dependent, up to 100 Hz per release notes, 25 Hz reported on fēnix 7 Pro); Garmin Health SDK (enterprise licence) streams accelerometer to a phone app | Raw data only; hardest runtime (Monkey C, small memory, no ML runtime) |

**Question 2 — training and deploying a model.** A wrist model is feasible on all four, but: (a) no public wrist dataset contains *real* falls — all wrist datasets are simulated falls by mostly young volunteers ([§4.2](#42-datasets)); (b) lab-trained detectors degrade strongly on real falls and free-living data (sensitivity 57 %, 3–85 false alarms/day in one benchmark, [Bagalà 2012](https://pmc.ncbi.nlm.nih.gov/articles/PMC3353905)); (c) synthetic data helps on some tasks but a wrist-watch study found *no gain or a loss* ([§4.5](#45-synthetic-data-generation)); (d) AMASS/SMPL-based synthesis pipelines are licensed **non-commercial only** ([AMASS licence](https://amass.is.tue.mpg.de/license.html)). The pragmatic route is a two-stage detector (threshold trigger → small 1D-CNN + inactivity check), trained on a pooled real-data base with synthetic data as supplement, fine-tuned and validated per device on your own recordings, and using each vendor's native fall event (Apple, Samsung) as a free weak label / safety net ([§5](#5-recommended-end-to-end-plan-ordered)).

### 2.1 Apple (watchOS / iOS)

#### A. Native fall detection — exposed? **Yes (event only).**

*Feature.* Apple Watch SE or later, Series 4 or later, and Ultra detect hard falls while worn; the watch taps, sounds an alarm and shows an alert; if the wearer is immobile for about a minute a 30-second countdown starts and then emergency services are called; falls are recorded in Health unless the user says they did not fall. It turns on automatically for users aged 55+ who entered their age; available only to users 18+; "Apple Watch cannot detect all falls" and "might detect high-impact activity as a fall" ([Apple Support](https://support.apple.com/en-us/108896)).

*Developer API.* `CMFallDetectionManager` (watchOS 7.2+) lets an app "request the user's authorization, and set up a delegate to receive notifications about these fall detection events" ([docs](https://developer.apple.com/documentation/coremotion/cmfalldetectionmanager)).
- **What the API delivers:** a `CMFallDetectionEvent` with `date` and `resolution` only ([event docs](https://developer.apple.com/documentation/coremotion/cmfalldetectionevent)). `resolution` ∈ `confirmed`, `dismissed`, `rejected`, `unresponsive` ([UserResolution](https://developer.apple.com/documentation/coremotion/cmfalldetectionevent/userresolution)). Delegate callback: `fallDetectionManager(_:didDetect:completionHandler:)` ([delegate](https://developer.apple.com/documentation/coremotion/cmfalldetectiondelegate)).
- **Behaviour documented:** real-time notification of "all fall events"; the system "wakes your app in the background" but gives "only a short amount of time to respond" before it may suspend the app; on launch the delegate receives the most recent recent event ([docs](https://developer.apple.com/documentation/coremotion/cmfalldetectionmanager)). Delegate must be set early (e.g. in `applicationDidFinishLaunching`), one manager instance only, user can revoke under Settings → Privacy → Fall Detection.
- **Requirements:** `NSFallDetectionUsageDescription` in Info.plist (otherwise the app crashes); entitlement `com.apple.developer.health.fall-detection` ("Fall Detection Notifications") obtained through Apple's [request form](https://developer.apple.com/contact/request/fall-detection-api/) (requires Apple ID sign-in; the form's content could not be read without login) ([entitlement docs](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.developer.health.fall-detection)). The entitlement "allows the app to run in the background without requiring any additional capabilities".
- **Alternative path:** HealthKit `numberOfTimesFallen` quantity samples — available on all devices that can access the person's HealthKit data, but "there can be a delay", and **dismissed alerts are not recorded** ([HealthKit docs](https://developer.apple.com/documentation/healthkit/hkquantitytypeidentifier/numberoftimesfallen)).
- **NOT exposed (per the docs read):** the sensor window that triggered detection, any confidence/score, detection thresholds or sensitivity settings, a way to trigger or tune detection, or the emergency-call decision. Whether third-party events fire when the user has switched the system Fall Detection setting off is not stated [UNVERIFIED].
- **Intended use stated by Apple:** "to provide assistance, or initiate communication with emergency services, in the event that someone falls" ([entitlement docs](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.developer.health.fall-detection)). The criteria Apple uses to approve the entitlement are not published [UNVERIFIED].

#### B. Raw sensors

| API | What | Rate / limits | Source |
|---|---|---|---|
| `CMMotionManager` | accelerometer, gyroscope, magnetometer, fused device-motion; per-sample real-time callbacks | "maximum supported frequency is 100 Hz" (WWDC23); interval is "capped… by the maximum frequency supported by the hardware" | [CMMotionManager](https://developer.apple.com/documentation/coremotion/cmmotionmanager), [WWDC23 10179](https://developer.apple.com/videos/play/wwdc2023/10179/) |
| `CMBatchedSensorManager` (watchOS 10+) | batched accelerometer and device-motion | 800 Hz accel, 200 Hz device-motion, one batch per second; **requires an active `HKWorkoutSession`**; "Apple Watch Series 8 and Ultra support both"; Apple notes this exposes "some of the same data streams that power… fall and crash detection" | [class](https://developer.apple.com/documentation/coremotion/cmbatchedsensormanager), [WWDC23](https://developer.apple.com/videos/play/wwdc2023/10179/) |
| `CMSensorRecorder` (watchOS 2+) | background accelerometer recorder | **50 Hz**; `recordAccelerometer(forDuration:)` up to 12 h "even if your app is suspended or terminated"; query ≤12 h ranges; data kept ≤3 days; up to ~3 min delay before samples are retrievable; needs `NSMotionUsageDescription` | [class](https://developer.apple.com/documentation/coremotion/cmsensorrecorder), [record](https://developer.apple.com/documentation/coremotion/cmsensorrecorder/recordaccelerometer(forduration:)), [query](https://developer.apple.com/documentation/coremotion/cmsensorrecorder/accelerometerdata(from:to:)) |
| `CMAltimeter` | relative/absolute altitude (barometer-derived) | availability via `isRelativeAltitudeAvailable()` | [CMAltimeter](https://developer.apple.com/documentation/coremotion/cmaltimeter) |
| HealthKit | heart rate etc. | HealthKit authorisation | [HealthKit overview](https://developer.apple.com/documentation/healthkit/about-the-healthkit-framework) |
| SensorKit | accelerometer/rotation-rate/heart-rate "from an iPhone or paired Apple Watch" | research-study approval only | [SensorKit](https://developer.apple.com/documentation/sensorkit), [entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.developer.sensorkit.reader.allow) |

Units: `CMAcceleration` values are in g ([docs](https://developer.apple.com/documentation/coremotion/cmacceleration)). Accelerometer full-scale range and gyroscope maximum rate on watchOS: not found [UNVERIFIED].

*Background limits.* Apple Watch apps are suspended when the wrist is lowered; background sessions "can only monitor workouts, track the user's location, or play audio files"; extended runtime sessions have fixed types (self care, mindfulness, physical therapy, smart alarm) and "select a session type based on the app's intended use"; high sustained CPU can cancel the session (`exceededResourceLimits`) ([Extended runtime docs](https://developer.apple.com/documentation/watchkit/using-extended-runtime-sessions)). **There is no documented "fall monitoring" session type** — so a custom always-on model cannot run continuously in the background on Apple Watch except (i) during a workout session, or (ii) by letting `CMSensorRecorder` buffer 50 Hz data and analysing it later, or (iii) by relying on `CMFallDetectionManager` for real-time events [INFERENCE from the documents above].

*Gyroscope in background:* `CMSensorRecorder` records **accelerometer only**; gyroscope needs live `CMMotionManager`/batched APIs (foreground or workout) [INFERENCE from the API surface].

#### C. Access / approval / cost
- Apple Developer Program: "$99 annual membership" ([Apple](https://developer.apple.com/programs/)).
- Fall-detection entitlement: manual request form; approval criteria and timing unpublished [UNVERIFIED].
- `CMBatchedSensorManager`: no entitlement documented, but needs HealthKit workout authorisation.
- SensorKit: study must be pre-approved by Apple ([Accessing SensorKit Data](https://www.researchandcare.org/resources/accessing-sensorkit-data/) is linked from the entitlement page).
- App Review 1.4.1: medical apps "that could provide inaccurate data… may be reviewed with greater scrutiny"; apps "must clearly disclose data and methodology to support accuracy claims" and remind users to consult a doctor ([App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/)).

#### D. Data egress / privacy
- HealthKit data is sent to your backend only by your own app code (no vendor cloud API for fall events was found [UNVERIFIED]); `WatchConnectivity` carries data to the iPhone app [not researched in this pass].
- App Review forbids "targeted or behavioral advertising based on sensitive user data such as health/medical data (such as from the HealthKit APIs)" ([guidelines](https://developer.apple.com/app-store/review/guidelines/)). HIPAA/GDPR positions are your responsibility; Apple's documents read do not claim HIPAA compliance for these APIs [UNVERIFIED].

#### E. On-device ML
- Core ML runs models "entirely on a person's device"; `MLModel` is available since watchOS 4.0 ([Core ML](https://developer.apple.com/documentation/coreml), [MLModel](https://developer.apple.com/documentation/coreml/mlmodel)). Convert PyTorch via `torch.jit.trace` or `torch.export` then `coremltools` ([convert guide](https://apple.github.io/coremltools/docs-guides/source/convert-pytorch-workflow.html)); weight quantisation options in [coremltools](https://apple.github.io/coremltools/docs-guides/source/opt-quantization-overview.html).
- Neural Engine availability on watch SoCs and per-op watchOS coverage: not verified [UNVERIFIED].

### 2.2 Samsung (Galaxy Watch — Wear OS powered by Samsung)

#### A. Native fall detection — exposed? **Yes, through Google Health Services.**

*Feature.* Galaxy Watch5/6/7/Ultra/Fit3 expose "Hard fall detection" in Galaxy Wearable → Safety and emergency; options include requiring a swipe before calling, when to detect falls, warning sound and sharing with contacts ([Samsung Support](https://www.samsung.com/us/support/answer/ANS00078032/)).

*Developer API.* Samsung's developer blog (Jan 18 2024, Wear OS 4) states: "Using the Health Services API, you can receive a fall detection event in your watch application" and shows the full pattern ([Events Monitoring](https://developer.samsung.com/health/blog/en/events-monitoring)):
- Dependency `androidx.health:health-services-client` (blog used `1.0.0-beta01`; the current docs show `1.1.0` — [Monitor data in the background](https://developer.android.com/health-and-fitness/health-services/monitor-background)).
- `PassiveMonitoringClient.setPassiveListenerServiceAsync(...)` with `PassiveListenerConfig.builder().setHealthEventTypes(setOf(HealthEvent.Type.FALL_DETECTED))`; a `PassiveListenerService` subclass overrides `onHealthEventReceived(event: HealthEvent)`; manifest permission `com.google.android.wearable.healthservices.permission.PASSIVE_DATA_BINDING`; runtime permission `ACTIVITY_RECOGNITION`; `FOREGROUND_SERVICE`, `RECEIVE_BOOT_COMPLETED`.
- `HealthEvent` carries `type` (`FALL_DETECTED` or `UNKNOWN`), event `Instant` and a `DataPointContainer` of "metrics associated with the event" ([HealthEvent](https://developer.android.com/reference/androidx/health/services/client/data/HealthEvent), [Type](https://developer.android.com/reference/androidx/health/services/client/data/HealthEvent.Type): "device detected that the user fell"). What metrics are actually populated for falls is not documented [UNVERIFIED].
- Capability check: `PassiveMonitoringCapabilities.getSupportedHealthEventTypes()` "on this device" ([reference](https://developer.android.com/reference/androidx/health/services/client/data/PassiveMonitoringCapabilities)) — **use it per watch model; which Galaxy Watch models/firmware return `FALL_DETECTED` is not listed by Samsung [UNVERIFIED]**.
- Testing without falling: emulator/`adb shell am broadcast -a "whs.FALL_OVER" com.google.android.wearable.healthservices` after `whs.USE_SYNTHETIC_PROVIDERS` ([Samsung blog](https://developer.samsung.com/health/blog/en/events-monitoring), [Android simulated-data doc](https://developer.android.com/health-and-fitness/health-services/simulated-data)).
- **NOT exposed:** raw trigger window, confidence, tuning, emergency-call control. Passive listener services are delivered in the background (passive monitoring "is intended for use cases that span hours, days" — [Android](https://developer.android.com/health-and-fitness/health-services/monitor-background)).
- No Samsung partner approval is mentioned for this path in the blog [UNVERIFIED that none is required in practice].

#### B. Raw sensors
- **Android `SensorManager`** (standard on Wear OS): accelerometer in m/s² including gravity, coordinate frame defined relative to the device screen (x right, y up, z out of the screen) ([SensorEvent](https://developer.android.com/reference/android/hardware/SensorEvent), [overview](https://developer.android.com/develop/sensors-and-location/sensors/sensors_overview)). Rates above 200 Hz need the `HIGH_SAMPLING_RATE_SENSORS` permission ([Manifest.permission](https://developer.android.com/reference/android/Manifest.permission)). Samsung notes the Galaxy Watch4's real hardware sensors are accelerometer, gyroscope, pressure, light, magnetic and PPG heart-rate; "sensors which appear in the logcat output may not be accessible for third-party developers" ([Samsung blog 2022](https://developer.samsung.com/sdp/blog/en/2022/05/25/check-which-sensor-you-can-use-in-galaxy-watch-running-wear-os-powered-by-samsung)) — check gyro/baro accessibility per model. Samsung's accelerometer tutorial says raw data are converted with `raw × 9.80665 / 4096` (8 g range) ([Samsung blog 2025](https://developer.samsung.com/sdp/blog/en/2025/04/10/understanding-and-converting-galaxy-watch-accelerometer-data)); maximum rate in this path not stated [UNVERIFIED].
- **Samsung Health Sensor SDK** (v1.4.1; Galaxy Watch4 series and later; no emulator): `ACCELEROMETER_CONTINUOUS` raw x/y/z at **25 Hz**; continuous trackers collect "in an application processor without waking up the CPU" and send events periodically; also `PPG_CONTINUOUS` (25 Hz), `HEART_RATE_CONTINUOUS` (1 Hz incl. IBI), skin temperature (Watch5+), EDA (Watch8+); ECG/BIA/SpO2 are on-demand foreground trackers ([overview](https://developer.samsung.com/health/sensor/overview.html), [data specs](https://developer.samsung.com/health/sensor/guide/data-specifications.html), [environment](https://developer.samsung.com/health/sensor/guide/environment.html)). **No gyroscope tracker** is listed; several continuous trackers can run simultaneously, only one on-demand tracker at a time ([FAQ](https://developer.samsung.com/health/sensor/faq.html)).
- *Background execution.* "Sensor data collection may stop when the screen is off"; Samsung recommends a **foreground service** (`foregroundServiceType="health"`) plus a **wake lock**, `BODY_SENSORS`, `BODY_SENSORS_BACKGROUND` (API 31+), `FOREGROUND_SERVICE_HEALTH` ([Samsung blog Apr 23 2026](https://developer.samsung.com/galaxy-watch/blog/en/2026/04/23/continuous-heart-rate-tracking-on-galaxy-watch-even-with-the-screen-off)). Battery cost of 24 h accelerometer streaming is not published [UNVERIFIED].
- Barometer: hardware pressure sensor present on Galaxy Watch4 and accessible to third parties (green in Samsung's sample app) ([Samsung blog 2022](https://developer.samsung.com/sdp/blog/en/2022/05/25/check-which-sensor-you-can-use-in-galaxy-watch-running-wear-os-powered-by-samsung)).

#### C. Access / approval / cost
- Sensor SDK: free download; **developer mode** on the watch (Settings → Apps → Health Sensor Service → tap title ~10 times) works for testing only; to distribute, submit a **partner request** registering the app's package name and SHA-256 signature, otherwise the SDK returns `SDK_POLICY_ERROR` ([process](https://developer.samsung.com/health/sensor/process.html), [developer mode](https://developer.samsung.com/health/sensor/guide/developer-mode.html), [verification](https://developer.samsung.com/health/sensor/guide/app-verification.html), [FAQ](https://developer.samsung.com/health/sensor/faq.html)). Approval timeline and fees: not stated [UNVERIFIED].
- Health Services / `SensorManager`: standard Android runtime permissions; no Samsung approval documented.
- Samsung Health Data SDK (phone, v1.1.0, Samsung Health ≥6.30.2): developer mode for testing; partner request before distribution; write access needs an access code ([overview](https://developer.samsung.com/health/data/overview.html), [process](https://developer.samsung.com/health/data/process.html)).

#### D. Data egress / privacy
- Watch→phone: Wearable Data Layer API (Google Play services) ([docs](https://developer.android.com/training/wearables/data/overview)); Samsung ships a "transfer measured heart rate to a connected phone" code lab ([environment page](https://developer.samsung.com/health/sensor/guide/environment.html)).
- Samsung Health Data SDK reads synced data types (heart rate, steps, sleep, exercise, SpO₂, IHRN… — **no raw accelerometer and no fall type** in the lists) ([overview](https://developer.samsung.com/health/data/overview.html)).
- Terms: data from Sensor SDK and Data SDK is "for fitness and wellness information only, not for the diagnosis or treatment of any medical condition" ([data specs](https://developer.samsung.com/health/sensor/guide/data-specifications.html), [Data SDK](https://developer.samsung.com/health/data/overview.html)). HIPAA/GDPR claims: none found [UNVERIFIED].

#### E. On-device ML
- Wear OS is Android-based: LiteRT (successor of TensorFlow Lite) and ONNX Runtime Android packages apply ([LiteRT for Android](https://ai.google.dev/edge/litert/android), [ONNX Runtime mobile](https://onnxruntime.ai/docs/tutorials/mobile/)). No Wear-OS-specific ML doc was found, so watch-class CPU/RAM limits and accelerator availability are [UNVERIFIED]; treat as CPU inference. PyTorch→LiteRT via the [LiteRT Torch converter](https://ai.google.dev/edge/litert/conversion/pytorch/overview); int8/float16/dynamic-range quantisation per [LiteRT PTQ guide](https://ai.google.dev/edge/litert/models/post_training_quantization) (dynamic range ≈4× smaller, 2–3× speed-up on CPU).


### 2.3 Huawei (HarmonyOS wearables, Wear Engine, Health Service Kit)

#### A. Native fall detection — exposed? **No developer API found.**

*Feature.* Huawei watches have fall detection + auto-SOS: "the watch will detect your posture through the accelerometer… If the watch detects a severe fall and senses that you are unable to move, it will enable the emergency SOS feature"; a pop-up asks whether to call, and after 60 s without input SOS triggers; Huawei states the feature is "not dedicated emergency assistance device/service", "may not detect all falls", and "may occasionally misinterpret high-impact activities as falls" ([Huawei Support](https://consumer.huawei.com/en/support/content/en-us16066705/)).

*Developer APIs reviewed — none exposes it:*
- **Wear Engine** open capabilities: wearable device info/status; phone↔wearable app messages and files; template notifications; "wearable user status" (query/subscribe **wearing status and heart-rate alerts**, *enterprise developers only*); device serial number (enterprise only) ([Service Introduction](https://developer.huawei.com/consumer/en/doc/connectivity-Guides/service-introduction-0000000000018585)). Permission scopes `DEVICE_MANAGER`, `NOTIFY`, `WEAR_USER_STATUS`, `DEVICE_SN` ([Applying for Wear Engine](https://developer.huawei.com/consumer/en/doc/connectivity-Guides/applying-wearengine-0000001050777982)). The intro mentions "sensor capabilities" only for Band 6 and "motion sensor" for S-TAG; no raw-accelerometer relay to phone apps is documented [UNVERIFIED that none exists].
- **Health Service Kit** cloud/device data-type tables: steps, calories, distance, altitude, intensity, heart rate, stress, sleep, SpO₂, temperature, ECG records, exercise records … **no fall event/type** ([Open Data Overview](https://developer.huawei.com/consumer/en/doc/HMSCore-Guides/data_description-0000001467889369), [smart-watch data](https://developer.huawei.com/consumer/en/doc/hmscore-guides/obtain-smart-watch-data-0000001365189921)).
- **Sensor Service Kit** sensor list has `SIGNIFICANT_MOTION`, `PEDOMETER_DETECTION`, `WEAR_DETECTION` etc., no fall sensor ([Sensor Overview](https://developer.huawei.com/consumer/en/doc/harmonyos-guides/sensor-overview)).
- These are negative findings from the listed pages; I did not exhaustively crawl Huawei's doc tree [UNVERIFIED negative]. Also not checked: Multimodal Awareness Kit (page not retrievable), Huawei-internal partner APIs.

#### B. Raw sensors (HarmonyOS watch app, ArkTS)
- `@ohos.sensor` (Sensor Service Kit) — wearable support from API 18 ([API reference](https://developer.huawei.com/consumer/en/doc/harmonyos-references/js-apis-sensor)). Sensor types include `ACCELEROMETER` (m/s², **includes gravity**), `LINEAR_ACCELEROMETER`, `GRAVITY`, `GYROSCOPE` (rad/s), `BAROMETER` (hPa), `HEART_RATE`, `WEAR_DETECTION`, `PEDOMETER`, `SIGNIFICANT_MOTION`, `ROTATION_VECTOR` ([Sensor Overview](https://developer.huawei.com/consumer/en/doc/harmonyos-guides/sensor-overview)).
- **Permissions:** `ohos.permission.ACCELEROMETER` and `ohos.permission.GYROSCOPE` are `system_grant` (no user prompt); `ohos.permission.ACTIVITY_MOTION` (pedometer) and `ohos.permission.READ_HEALTH_DATA` (heart rate) are `user_grant` ([Sensor Overview](https://developer.huawei.com/consumer/en/doc/harmonyos-guides/sensor-overview)).
- **Sampling:** `sensor.on(id, cb, {interval})`; "minimum and maximum sampling periods supported by the sensor are 5000000 ns and 200000000 ns" (200 Hz … 5 Hz) and "may vary depending on the sensor type"; requests outside the range are clamped ([Sensor Development (ArkTS)](https://developer.huawei.com/consumer/en/doc/harmonyos-guides/sensor-guidelines)). Actual hardware rates on WATCH 5 / Ultimate 2 etc.: not documented [UNVERIFIED]. Axes: defined by the device's natural screen direction (X left→right, Y bottom→top, Z out of screen), "may vary according to device models" ([Sensor Overview](https://developer.huawei.com/consumer/en/doc/harmonyos-guides/sensor-overview)).
- **Device support:** "Wearables" = HarmonyOS 5.1+ watches (WATCH 5, WATCH Ultimate 2, WATCH KIDS X) with "high-precision health data APIs, an on-device AI inference engine" ([Wearables overview](https://developer.huawei.com/consumer/en/multidevice/wearables), [Wearable App Development](https://developer.huawei.com/consumer/en/doc/best-practices/bpta-smartwatch)); older "lite wearables" have a separate "low-power sensor data API" architecture ([Wearables overview](https://developer.huawei.com/consumer/en/multidevice/wearables)); the emulator does not support wearable app development for Health Service Kit ([Health Service Kit intro](https://developer.huawei.com/consumer/en/doc/harmonyos-guides/health-service-kit-ability)).
- **Background:** Continuous Task types listed are data transfer, audio, recording, location, Bluetooth, multi-device, VoIP, task-keeping (non-PC needs ACL permission `KEEP_BACKGROUND_RUNNING_SYSTEM`), AV record, special scenario (phones/tablets/PCs only), NearLink — **no sensor/health/fall type** ([Continuous Task](https://developer.huawei.com/consumer/en/doc/harmonyos-guides/continuous-task)). Sensor Service "manages foreground and background policies" ([Sensor Overview](https://developer.huawei.com/consumer/en/doc/harmonyos-guides/sensor-overview)). Whether a watch app can keep subscribing to the accelerometer with the screen off is therefore **not documented** [UNVERIFIED]; per-device lifecycle differences are described on a page I could not retrieve.
- **Phone side:** Huawei Health only syncs aggregate data (hour/minute-level timeliness) to Health Service Kit; no raw IMU ([Open Data Overview](https://developer.huawei.com/consumer/en/doc/HMSCore-Guides/data_description-0000001467889369)).

#### C. Access / approval / cost
- Sensor Service Kit: **no approval**, just `system_grant` permissions in `module.json5` ([Sensor Development](https://developer.huawei.com/consumer/en/doc/harmonyos-guides/sensor-guidelines)).
- Wear Engine: register a HUAWEI ID, apply in AppGallery Connect → Wear Engine; **individual developers can only apply for basic device information and message notification permissions**; user status (wearing, HR alerts) and device SN are enterprise-only ([Applying](https://developer.huawei.com/consumer/en/doc/connectivity-Guides/applying-wearengine-0000001050777982)).
- Health Service Kit: AppGallery Connect application with justification; "manual review… takes about 10 working days"; test permissions limit use to the **first 100 users**; formal permissions must be requested within one year; random post-release checks; for phones/tablets the kit is "supported only in the Chinese mainland" ([Apply](https://developer.huawei.com/consumer/en/doc/harmonyos-guides/health-apply), [intro](https://developer.huawei.com/consumer/en/doc/harmonyos-guides/health-service-kit-ability)); advanced data types are enterprise-only ([Open Data Overview](https://developer.huawei.com/consumer/en/doc/HMSCore-Guides/data_description-0000001467889369)).

## 4. Part B — training and deploying a wrist fall-detection model

### 4.1 Problem framing

**Task.** Binary (or 3-class: fall / near-fall-or-stumble / ADL) detection from wrist IMU windows: tri-axial accelerometer, usually tri-axial gyroscope, optionally barometer (relative altitude change) and heart rate. Most datasets provide simulated falls onto a mattress; labels are per trial, sometimes with fall-onset/impact frame labels (KFall, WEDA-FALL).

**Why the wrist is hard** (what the sources support):
- The wrist is the most active limb in daily life, so impacts and large-magnitude arm motions that resemble falls are common (clapping, tabletop slams, sports, catching oneself). Apple itself warns the watch "might detect high-impact activity as a fall" ([Apple](https://support.apple.com/en-us/108896)); so does Huawei ([Huawei](https://consumer.huawei.com/en/support/content/en-us16066705/)).
- Lab comparisons across body locations find the wrist worst: best wrist sensitivity 97.37 % vs 99.96 % at the waist ([Özdemir 2016](https://pmc.ncbi.nlm.nih.gov/articles/PMC5017327)); an earlier study with three middle-aged subjects judged the wrist "not… an applicable site" ([Kangas 2008](https://pubmed.ncbi.nlm.nih.gov/18294851/)). A protective arm reflex can decouple wrist motion from trunk impact [INFERENCE — plausible mechanism, not shown in the sources].
- Wrist data from a loose watch strap adds relative motion not present on waist/chest sensors [INFERENCE].
- Real falls differ from simulated ones; the Casilari dataset survey reports, citing Klenk and Mehner, that real falls are faster and more irregular than mimicked ones, while Kangas found a similar profile ([Casilari 2017](https://pmc.ncbi.nlm.nih.gov/articles/PMC5539544); secondary citation — verify in the original papers).

**Windowing.** Falls are short (impact ≈ <1 s) but the full event (pre-impact descent, impact, post-impact stillness) spans several seconds. Published wrist work uses 9 s windows at 50 Hz with a 3-NN on features ([WEDA-FALL paper](https://pmc.ncbi.nlm.nih.gov/articles/PMC9920426/)) and "short, fixed-length windows" with 1D-CNNs ([Gated-CNN](https://arxiv.org/abs/2605.20275)). Recommended here: an event-triggered **4–6 s window centred ~1.5–2 s after the trigger**, plus a separate **10–60 s post-impact inactivity check** (Apple's own flow waits ~1 minute of immobility before escalation — [Apple](https://support.apple.com/en-us/108896)) [INFERENCE for the specific numbers; tune empirically].

**Sampling rate.** Public wrist data: 31.25 Hz (SmartFall), 50 Hz (WEDA-FALL), 100 Hz (UP-Fall), 238 Hz (FallAllD). Platform ceilings differ: Samsung Sensor SDK 25 Hz, Garmin often 25 Hz (up to 100 Hz where supported), Apple 50 Hz (recorder) / 100 Hz (live), Huawei ≤200 Hz. Choose a **canonical 50 Hz** model plus a **25 Hz variant** (decimate with an anti-alias filter) so a single training set serves all four [INFERENCE]. Watch impact peaks can exceed the full-scale range of low-g settings (Samsung's conversion implies an 8 g range; FallAllD uses ±8 g, SisFall's ADXL345 ±16 g) — **simulate clipping** at the target range [INFERENCE].

**Preprocessing.** Convert units to g, resample to a uniform grid by timestamps (do not trust callback cadence — Apple/Garmin/Android all deliver batches), band-limit (e.g. 0.3–20 Hz) for the model branch, retain a low-pass gravity estimate (<0.5 Hz) as orientation cue, optional magnitude and tilt-angle channels; per-window clipping and normalisation by fixed physical scale (not per-window z-score, which erases impact magnitude) [INFERENCE].

**Features vs end-to-end.** Feature + classical ML baselines remain competitive and cheap (3-NN on handcrafted features achieved zero false positives/negatives over four days of live testing in a small study — [WEDA-FALL paper](https://pmc.ncbi.nlm.nih.gov/articles/PMC9920426/)); deep models "generalize better to new users" and beat SVM/Naive Bayes on three datasets ([SmartFall](https://pmc.ncbi.nlm.nih.gov/articles/PMC6210545)). Neither claim is validated on large free-living older-adult data.

**Metrics.** Report per-fall-type **sensitivity**, **specificity**, and — most important for acceptance — **false alarms per day (or per hour) on free-living recordings**, plus **latency** (impact → alert) and **time-to-escalation**. Benchmarks to compare with: real-world falls, 13 published algorithms: sensitivity 57.0 ± 27.3 %, specificity 83.0 ± 30.3 %, **3–85 false alarms/day** in three fallers ([Bagalà 2012](https://pmc.ncbi.nlm.nih.gov/articles/PMC3353905)); SVM with waist/sternum accelerometer: 8/10 real falls, 0–0.3 false alarms/hour in older adults ([Aziz 2017](https://pmc.ncbi.nlm.nih.gov/articles/PMC5498034)); FARSEEING lower-back, 143 real falls: sensitivity >80 % at 0.56 false alarms/hour ([Palmerini 2020](https://pmc.ncbi.nlm.nih.gov/articles/PMC7697900)). Accuracy/F1 on balanced lab sets says little.

**Class imbalance.** Falls are rare: use inverse-frequency or focal loss, hard-negative mining from free-living ADL, report PR curves and choose the operating point from a **false-alarm budget** (e.g. ≤1/day) rather than from F1 [INFERENCE]. Do *not* use SMOTE-style interpolation across fall postures blindly ([§4.5.4](#454-augmentation)).

### 4.3 Evidence on generalisation and evaluation pitfalls

- **Lab → real:** sensitivity dropped to 57 % on real falls ([Bagalà 2012](https://pmc.ncbi.nlm.nih.gov/articles/PMC3353905)); models trained on many lab datasets "showed a remarkable degradation in all performance metrics (sensitivity, specificity and false alarm hourly rate)" on real falls and long-term daily-life traces ([Casilari et al., Measurement 2024](https://www.sciencedirect.com/science/article/pii/S0263224124008777) — abstract only; full text not read).
- **Cross-dataset wrist generalisation:** pooling UP-Fall, UMAFall and WEDA-FALL (over 1,300 falls and 28 K ADL samples) reached recall 90.57 %, specificity 96.91 %; but **cross-dataset F1 peaked at ≈70 %**, "significantly lower" than within-dataset, and small single datasets give "overoptimistic classification rates" ([Fula & Moreno 2024](https://pmc.ncbi.nlm.nih.gov/articles/PMC10935140)).
- **Commodity watches in the wild:** a Transformer on hip+wrist data reached F1 88 % offline but "produced a high number of false positives" in an uncontrolled home; retraining with ten participants' false-positive/true-positive feedback gave F1 92 % with fewer false positives ([Sensors 2025](https://pmc.ncbi.nlm.nih.gov/articles/PMC12431052)). A May 2026 preprint reports Gated-CNN F1 90–93 % on five wrist datasets and F1 97 %, zero missed falls, in a 12-participant Pixel Watch 3 test ([arXiv 2605.20275](https://arxiv.org/abs/2605.20275); preprint, small test, simulated falls [INFERENCE on the last two caveats]).
- **Leakage:** record-wise k-fold inflates HAR accuracy by ~10 %, up to 16 % with overlapping windows; use **subject-wise** splits ([Dehghani et al.](https://arxiv.org/abs/1904.02666)). Never put windows from one trial, or the same subject, on both sides of a split; report cross-dataset results too.
- **Young vs elderly:** SisFall/KFall/UP-Fall subjects are young; WEDA-FALL's elderly performed only ADLs. Only the 2025 Sensors study and SmartFall's follow-up report elderly participants ([PMC12431052](https://pmc.ncbi.nlm.nih.gov/articles/PMC12431052), [follow-up](https://pmc.ncbi.nlm.nih.gov/articles/PMC9919743/)). Expect an age gap (slower, softer, longer falls) [INFERENCE].

### 4.4 Model options and recommendation

| Option | Pros | Cons / notes | Suitable where |
|---|---|---|---|
| **Threshold cascade** (e.g. free-fall dip → impact peak → post-impact orientation/stillness) | Tiny, interpretable, ports to Monkey C | Poor on real falls: 13 threshold/rule algorithms scored sensitivity 57 % on real falls ([Bagalà](https://pmc.ncbi.nlm.nih.gov/articles/PMC3353905)); wrist worst placement ([Kangas](https://pubmed.ncbi.nlm.nih.gov/18294851/)) | Always-on **trigger stage** on every platform; sole detector on Garmin |
| **RF / XGBoost / k-NN on features** (magnitude stats, jerk, tilt, spectral, impact-to-stillness ratios) | Cheap, small, easy to export to code; strong baseline | Feature engineering per fs; cross-dataset drop ([Fula & Moreno](https://pmc.ncbi.nlm.nih.gov/articles/PMC10935140)) | Garmin (compile trees to Monkey C), baseline everywhere |
| **1D-CNN (3–4 conv blocks + GAP)** | Good accuracy/size; low latency | Needs diverse negatives | **Recommended core classifier** (≈10⁴–10⁵ params, int8 ≲100 KB [INFERENCE]) |
| **Dual-stream gated 1D-CNN** (separate accel/gyro stems + sigmoid gating) | Reported to beat Transformer baselines on 5 wrist datasets; light ([arXiv 2605.20275](https://arxiv.org/abs/2605.20275)) | Preprint | Strong candidate architecture |
| CNN-LSTM / GRU | Used in SmartFall-style RNNs (DL > SVM/NB, better new-user generalisation — [SmartFall](https://pmc.ncbi.nlm.nih.gov/articles/PMC6210545)) | Recurrent ops add conversion risk on Core ML/MindSpore Lite | Optional |
| **TCN** | Parallel, conv-only → easy to export/quantise | Larger receptive field costs memory | Good alternative to CNN [INFERENCE] |
| Small Transformer | Higher offline F1 with multi-sensor input (88 %, [PMC12431052](https://pmc.ncbi.nlm.nih.gov/articles/PMC12431052)) | Quadratic cost, more false positives at deployment; the Gated-CNN paper argues attention is poorly suited to short impact windows | Not recommended for watch inference |

**Recommended architecture (all platforms except Garmin):** 2-stage detector — (1) always-on, ~25–50 Hz **impact trigger** (|a| spike and/or free-fall dip, rotation burst), cheap enough to run on-sensor-hub/batched; (2) **dual-stream gated 1D-CNN** on a 4–6 s window around the trigger, input 6×(fs·window), ~20–60 k parameters, int8; (3) **inactivity/orientation verifier** over the following 10–60 s and a **user-confirmation UI** with a countdown (mirroring Apple's 30 s countdown [Apple](https://support.apple.com/en-us/108896)) before any emergency escalation. On Garmin use stage 1 + a compiled tree/logistic head.


### 4.5 Synthetic data generation

**Bottom line first.** Published evidence that synthetic IMU data helps is real but task-dependent, and **weakest exactly where this project lives**: subtle/short wrist motions on a watch. The one watch-specific fall study found no gain; a large virtual-IMU comparison found no significant gain on Apple Watch wrist data. Use synthetic data to (a) widen **negatives and rare fall postures** and (b) **pre-train**, always validate on **real, subject-disjoint, device-specific** data, and drop it if it does not beat the real-only baseline.

#### 4.5.1 Physics / biomechanics simulation → virtual wrist IMU

*Principle.* Generate a body motion (mocap, video-derived, simulated, or text-generated), attach a virtual IMU at the wrist, and compute: specific force `a_meas = Rᵀ(a_world − g)` (+ bias, noise, scale, misalignment, clipping, quantisation), angular velocity from orientation differences. Deep Inertial Poser computes accelerations by finite differences of virtual-sensor positions on an SMPL mesh, `a_t = (p_{t−1}+p_{t+1}−2p_t)/(2·dt)`, orientations from forward kinematics, notes "subtle differences between real and synthesized accelerations", and fine-tunes on real IMU data ([DIP, arXiv 1810.04703](https://arxiv.org/abs/1810.04703)). TransPose warns synthesized data "should not be directly used in training" without normalisation/frame transformation ([TransPose README](https://github.com/Xinyu-Yi/TransPose)).

> **⚠ Licence trap for commercial use.** AMASS is licensed for "non-commercial scientific research… Any other use, in particular any use for commercial purposes, is prohibited… This licence also prohibits the use of the Dataset to train methods/algorithms/neural networks/etc. for commercial use of any kind" ([AMASS licence](https://amass.is.tue.mpg.de/license.html)). SMPL has the same restriction, with commercial licences via Meshcapade ([SMPL licence](https://smpl.is.tue.mpg.de/modellicense.html)); SMPL-X adds a military/surveillance ban ([SMPL-X](https://smpl-x.is.tue.mpg.de/modellicense.html)). HumanML3D "originates from… HumanAct12 and Amass" and cannot be redistributed ([repo](https://github.com/EricGuo5513/HumanML3D)). Whether weights of text-to-motion models trained on such data count as "training for commercial use" is a legal question no primary page answers. DIP/TransPose-style AMASS→IMU synthesis and IMUGPT-style pipelines therefore need a **commercial licence** (ps-license@tue.mpg.de / Meshcapade) or a pipeline that avoids these assets (own mocap, MuJoCo/OpenSim humanoids, own video + a non-SMPL body model).

#### 4.5.3 Generative models for IMU time series

- **TimeGAN** (Yoon, Jarrett, van der Schaar, NeurIPS 2019): general time-series GAN with supervised embedding; repo uses sine/stock/energy data only; repo licence file contains the Apache-2.0 header ([repo](https://github.com/jsyoon0823/TimeGAN)). No fall/IMU results verified.
- **Diffusion-TS** (Yuan & Qiao, ICLR 2024; MIT): general time-series diffusion; used as a fall-data generator in the Alamgeer study (lowest Jensen-Shannon divergence, SMM 0.1399, KFall 0.2168, **but not consistently better classification**) ([OpenReview](https://openreview.net/forum?id=4h1apFjO99), [repo](https://github.com/Y-debug-sys/Diffusion-TS), [PMC12390476](https://pmc.ncbi.nlm.nih.gov/articles/PMC12390476)).
- **IMUDiffusion** (Oppel & Munz, 2024): diffusion for multivariate IMU series; abstract reports macro-F1 improved "by almost 30 %" in some cases when real data are joined with synthetic ([arXiv 2411.02954](https://arxiv.org/abs/2411.02954)); code/licence not stated on the abstract page.
- **Caveat.** Low distribution divergence ≠ better detector. Generative models trained on a few dozen simulated falls mainly reproduce the simulation's biases (soft mattress impacts, young subjects) [INFERENCE supported by Alamgeer's result above].

#### 4.5.4 Augmentation

- **Transformations** (Um et al. ICMI 2017, [arXiv 1706.00527](https://arxiv.org/abs/1706.00527)): jitter, scaling, rotation, permutation, magnitude-warping, time-warping; Parkinson's monitoring classification rose "from 77.54 % to 86.88 %" with suitable augmentation. Surveys: [Iwana & Uchida 2021](https://journals.plos.org/plosone/article?id=10.1371/journal.pone.0254841) (12 methods, 128 UCR datasets; rotation helped in Um et al., but other work saw no effect or harm) and [Wen et al. 2021](https://arxiv.org/abs/2002.12478). In a virtual-IMU comparison a fixed z-rotation + noise + bias did not beat real-only (PAMAP2 RF 47.6 % vs 48.1 %) ([arXiv 2506.07612](https://arxiv.org/abs/2506.07612)).
- **Window slicing / random crops** around the impact (±0.5 s shifts) are safe and simulate trigger-timing jitter [INFERENCE].
- **SMOTE** ([Chawla et al. 2002](https://www.jair.org/index.php/jair/article/view/10302)) interpolates minority samples; on time-series windows it blends impact timing and posture and produces physically impossible signals — prefer class weights, hard-negative mining and physics-based synthesis [INFERENCE].
- **Cautions specific to IMU.** (1) Rotation augmentation must be applied **jointly to accelerometer and gyroscope vectors with the same rotation matrix** and must preserve the gravity direction cue if your model uses tilt; limited, wrist-plausible rotations (±30° about the forearm axis, mirrored for left/right) are safer than arbitrary 3-D rotation. (2) Scaling accel by >1.2 can create impacts a human cannot produce; clip to sensor range. (3) Time-warp changes apparent fall duration; keep within ±15 %. (4) Never augment before splitting by subject. (5) Orientation-invariant formulations exist ([Yurtman & Barshan 2017, PMC5579846](https://pmc.ncbi.nlm.nih.gov/articles/PMC5579846); not read in detail) but discard tilt information useful for lying-posture detection [INFERENCE]. All numeric ranges here are [INFERENCE]; tune on validation subjects.

#### 4.5.5 Sim-to-real gap handling

1. **Domain randomisation** ([Tobin et al. 2017](https://arxiv.org/abs/1703.06907), an image-based robotics result with no IMU evidence) — applied to IMU by randomising body height/mass, wrist position and strap rotation, watch tightness/slip, motion speed, impact surface stiffness, sensor noise/bias/scale, clipping range and sampling jitter (Tang et al. did model scaling + IMU-placement perturbation) [INFERENCE].
2. **Distribution calibration with a little real data** — IMUTube rank-transform mapping to a small real sample; IMUGPT calibrates with a small amount of real data; DIP pre-trains on synthetic and fine-tunes on real ([arXiv 2006.05675](https://arxiv.org/abs/2006.05675), [DIP](https://arxiv.org/abs/1810.04703)).
3. **Fine-tune on real, per-device data** — the Sensors 2025 feedback retraining (F1 88 → 92 %, fewer false positives) is the best fall-specific evidence ([PMC12431052](https://pmc.ncbi.nlm.nih.gov/articles/PMC12431052)).
4. **Domain adaptation / transfer** — surveys: [Chen et al., arXiv 2001.07416](https://arxiv.org/abs/2001.07416) (deep learning for sensor HAR, challenges); [Dhekane & Plötz, arXiv 2401.10185](https://arxiv.org/abs/2401.10185) (transfer learning in HAR; cited in 2506.07612, not opened) [UNVERIFIED content]. Practical options: DANN/MMD alignment between sim and real features, per-device input-normalisation layers, adapter fine-tuning [INFERENCE].
5. **Validation rule.** Evaluate only on **real held-out subjects recorded on the target watch**; compare against real-only training; track **false alarms/day on free-living recordings** because synthetic negatives rarely cover the real tail.

#### 4.5.6 Concrete synthetic pipeline (license-safe)

1. *Motion sources (no AMASS/SMPL):* (a) your own mocap/IMU rig recordings of scripted falls and ADLs; (b) OpenSim or MuJoCo humanoid with falls driven by randomised initial conditions (trip, slip, faint, sit-collapse, stair); (c) your own video of staged falls → pose estimator → OpenSim IK (the Tang et al. recipe).
2. *Virtual IMU at the wrist:* sensor model with 3-D mounting offset and random rotation about the forearm, strap-slip low-pass/lag term, bias/scale/misalignment, white + 1/f noise from the target part's datasheet, ±8 g/±16 g clipping, 12–16-bit quantisation (Garmin: integer milli-g), device-specific band-limiting then decimation to 25/50 Hz, timing jitter.
3. *Hard negatives:* simulate/record wrist-impact ADLs (table slams, clapping, door closing, sitting hard, stumble-recover, sports swings, running/stairs, driving bumps, arm flailing while seated).
4. *Mix:* start with real:synthetic 1:1 per class; sweep synthetic fraction; stop when real-validation false alarms/day or sensitivity stop improving.
5. *Pre-train on synthetic, fine-tune on real*, with synthetic-only runs as an ablation, subject-wise CV and cross-dataset tests.
6. *Document* data lineage and licences for every motion and model asset.

**Expected pitfalls (cumulative):** simulated impacts on mats are softer than real ones; sims lack strap slip and clothing; gyro realism is weaker than accel (Tang et al.); text-to-motion data is unstable at high sampling rates (Alamgeer); virtual-IMU gains vanish for fine-grained wrist motion (Leng et al.); synthetic falls from young-body rigs ≠ older-adult kinematics [INFERENCE]; label noise at fall onset (WEDA-FALL's timestamps "manually assembled, possibly with errors" — [repo](https://github.com/joaojtmarques/WEDA-FALL)).

**Recommended canonical format** (a convention to adopt, not a vendor standard): float32, **accel in g with gravity**, **gyro in rad/s**, a right-handed *wrist frame* defined as x = along forearm toward fingers, y = across the wrist toward thumb side, z = out of the watch face (flip signs so that a flat, face-up watch reads +1 g on z), fixed **50 Hz** (and 25 Hz) uniform grid from timestamps, left-wrist canonical (mirror right-wrist: negate y and the corresponding gyro axes — verify mirroring on data), per-record metadata `{vendor, model, firmware, wrist, crown_side, range, native_rate}`. Implement a per-vendor adapter with a **calibration check**: record the watch lying flat face-up, face-down and on each edge, and assert the gravity vector signs/axes after the adapter; conventions differ and the gravity sign convention can silently flip (Android's accelerometer reports +9.81 m/s² on z when flat face-up — "acceleration minus Gz" — but Apple's convention must be verified on-device) [INFERENCE; verify].

**Other cross-device pitfalls.** Different on-sensor filtering (fused vs raw channels, `userAcceleration` removes gravity); batching and timestamp jitter (Apple 1-s batches, Garmin ≤4-s periods, Samsung continuous events); integer quantisation/scaling (Garmin milli-g ints, Samsung 8 g rescale); sensor range clipping; case/strap geometry and mass (Ultra vs Series, Ultimate vs Fit), left/right wrist and crown-side settings; 25 Hz devices cannot represent the impact spike seen at 238 Hz in FallAllD (train a 25 Hz-native variant, not just a 238→25 Hz downsample without anti-aliasing).

**Per-device calibration strategy.** (1) Train the base on pooled public wrist data + synthetic. (2) Collect a **small own dataset on every target watch** — suggested ≥15–20 subjects × (scripted falls on mat in ≥8 types + ≥50 hard-negative ADL motions) plus **multi-day free-living wear** for false-alarm measurement [INFERENCE on counts]. (3) Fine-tune last layers/adapters per device family and validate on held-out *subjects and days*. (4) Use Apple/Samsung native fall events as weak labels during field pilots (see §5 step 7).

### 4.8 Safety, regulatory and privacy caveats

- **Vendors' own positions.** Samsung SDK data is "for fitness and wellness information only, not for the diagnosis or treatment of any medical condition" ([data specs](https://developer.samsung.com/health/sensor/guide/data-specifications.html)); Huawei: feature "not [a] dedicated emergency assistance device/service" ([Huawei](https://consumer.huawei.com/en/support/content/en-us16066705/)); Apple "cannot detect all falls" ([Apple](https://support.apple.com/en-us/108896)); Garmin makes the developer responsible for FDA/MHRA/etc. compliance ([Connect IQ Agreement](https://developer.garmin.com/downloads/connect-iq/sdks/agreement.html)); Apple App Review 1.4.1 requires disclosure of "data and methodology to support accuracy claims" and doctor reminders ([Guidelines](https://developer.apple.com/app-store/review/guidelines/)).
- **US.** FDA's General Wellness guidance (reissued **January 6, 2026**) covers low-risk wellness products and excludes those "intended for the diagnosis, cure, mitigation, prevention, or treatment of a disease or condition" or that "include claims, functionality, or outputs that prompt or guide specific clinical action" ([FDA](https://www.fda.gov/media/90652/download?attachment)). Whether an automated fall alert that summons emergency help is a "wellness" function is not answered in the text I read — [INFERENCE] it likely falls outside the safe harbour once marketed as detection/alerting for at-risk people; obtain regulatory advice before any claim.
- **EU.** MDR Rule 11 (software to monitor physiological processes) and qualification criteria are in [MDCG 2019-11](https://health.ec.europa.eu/system/files/2025-06/mdcg_2019_11_en.pdf); whether fall alerts qualify depends on intended purpose [INFERENCE]. Health data is special-category personal data under GDPR (recital 35 defines "personal data concerning health": [GDPR](https://eur-lex.europa.eu/legal-content/EN/TXT/?uri=CELEX:32016R0679); Art. 9 text not re-read in this pass).
- **Product design.** Avoid medical-grade/"prevents injury" claims; state limitations like Apple/Huawei do; make **false-alarm burden** a release criterion (set a cap per user per day); require **explicit consent** and per-feature permissions (Apple's separate fall-detection authorisation is a model); give a cancel countdown (Apple: 30 s) and escalate to *emergency contacts* first unless the user opts into calling emergency services; handle dual alerts with native OS fall features (Apple/Samsung may already call emergency services — avoid double-escalation); log and retain minimal data; support user deletion; test with older adults.
- **Network dependency.** Alert delivery requires phone/LTE/Wi-Fi: Apple needs cellular, Wi-Fi calling or nearby iPhone ([Apple](https://support.apple.com/en-us/108896)); Garmin needs LTE or Bluetooth to a phone with data and the watch worn ([Garmin](https://support.garmin.com/en-US/?faq=RfaXahBWkH8Q7pVFLsuUmA)); design offline fallbacks (local alarm).

## 5. Recommended end-to-end plan (ordered)

1. **Decide scope & claims.** Product = "wellness fall-alert assistant", not a medical device, pending regulatory advice (§4.8). Define the false-alarm budget (e.g. ≤1/user/day) and a minimum sensitivity on scripted falls.
2. **Per-platform feasibility spike (1–2 weeks).** Apple: request the Fall Detection entitlement; build a Watch app logging `CMMotionManager` 50–100 Hz inside a workout session and `CMSensorRecorder`. Samsung: Health Services `FALL_DETECTED` + `SensorManager`/Sensor SDK logging in a `health` foreground service; apply for Samsung partner status early. Huawei: HarmonyOS watch app logging `@ohos.sensor` accel/gyro; test screen-off behaviour (undocumented). Garmin: Connect IQ device app logging `registerSensorDataListener`; call `getMaxSampleRate()` on target devices; decide Health SDK enterprise vs Monkey C-only.
3. **Build the canonical data layer** (§4.6): adapters, unit/axis/rate normalisation, flat-watch calibration tests, metadata schema.
4. **Assemble real training data.** Pool UP-Fall, UMAFall, FallAllD, WEDA-FALL, SmartFall, Erciyes (check licences before commercial training; UMAFall/Erciyes are CC BY 4.0), and negotiate permission for the rest. Resample to 50/25 Hz with anti-aliasing. Subject-wise splits, plus leave-one-dataset-out.
5. **Train baselines**: threshold trigger, feature + RF/XGBoost, gated 1D-CNN. Report sensitivity/specificity, PR, false alarms per simulated day (replay free-living ADL).
6. **Add synthetic data (license-safe pipeline, §4.5.6)** and run the ablation: real-only vs +synthetic vs synthetic-pretrain+real-fine-tune; keep only if real-validation improves.
7. **Collect your own per-device dataset**: scripted falls on mats (spotter, ≥15 subjects incl. older adults where ethical approval allows), hard-negative ADL, and multi-day free-living wear.
